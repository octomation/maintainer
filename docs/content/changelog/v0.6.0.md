# v0.6.0 — Reviews in one form.

Maintainer v0.6.0 ships a second agent skill. With the updated plugin, your coding agent offers `maintainer:review` next to `maintainer:maintainer`: it writes a code, issue or security review of a repository as one report in a fixed form. The `maintainer skill` commands install, check and export both skills, and the maintainer skill gives more of the answers that users ask for. Nothing changes in your configuration, state or the hub.

## The review skill

- Ask your agent for a review report, such as “write a code review report”. A code review asks whether you can release the code, an issue review whether the backlog states the truth, and a security review who can harm your users or your release channel.
- Each report has a table of findings with a severity and a verdict that follows from it. The skill checks the form with its own script before it hands the report over.
- It takes the checks to run, the threat model and the issue codes from your project, and states the default it used where the project names none. Issue codes come from an issue mirror in `.github/issues/`, or from GitHub issues such as `#12`.
- Code and issue reports go to `.github/reviews/`. A security report stays private in `.agents/reviews/`, and the skill refuses to write it there unless Git ignores the folder.
- The skill needs `python3` and Git; without an issue mirror, it reads the state of your issues with a signed-in `gh`.

## The skill commands

- `maintainer skill install`, `status`, `info`, `show` and `export` handle both skills. `--skill` selects them; without it, a command takes both.
- `skill info --json` prints one JSON object per skill, each with its `name`, one per line. A script that read the single object of v0.5.2 now reads the first line, the maintainer skill.
- `skill export -o <dir>` writes each skill into its own folder, `<dir>/maintainer` and `<dir>/review`. v0.5.2 wrote the skill into `<dir>` itself; a directory that holds a skill is now refused, so pass the directory above it.
- A `review` folder that another tool installed is not a copy of this skill: `install` and `export` skip it with a note, unless `--skill review` names it.
- `skill status` finds the catalog plugin by its name, `maintainer`, and judges it as a whole: with `--exact`, a plugin without the review skill fails.

## The maintainer skill

- When the skill and the binary differ, the agent asks `maintainer skill status` where the skill comes from and updates it there: a plugin copy with the agent’s plugin manager, a copy from the binary with `maintainer skill install --replace`. It no longer installs a second copy next to a plugin.
- The contribution commands take the token from `GITHUB_TOKEN` only, and the skill says so. Their recipe names the default anchor, the use with `git commit --date` and the exits `2` and `4`.
- The skill knows `[[repos]] ignore = true`, `clone_url`, `[[owners]] path`, and the `[fetch] config` and `[[repos]] weight` keys of the service. It names `-vv` and `-vvv`, the exit codes of `skill` and `service`, and every field of `status --format=json`.

## Known limitations

- The catalog plugin and the binary carry the same skills only from v0.6.0 on: a plugin of an older release has the maintainer skill alone, and `skill status --exact` reports it.
- `fetch` refuses a working directory reached through a symlink when the workspace root is that directory.
- The hub speaks plain HTTP. A program of another account that takes the port after the service stops sees the addresses that an open tab still requests. On a computer with other accounts, close the tabs of the hub before you stop the service.
- A change that keeps the total of a month, such as one contribution removed and another added, is not seen until the folder of fast repeat runs is deleted.
- An issue opened in the browser near midnight keeps the browser's date on the profile, and the contribution commands may put it a day off.
- The contribution commands count by calendar year, not by the profile's rolling twelve months.

**Upgrade:** with Homebrew, run `brew update` followed by `brew upgrade --formula octolab/tap/maintainer`. With the install script, pass the tag: `sh -s -- -b ~/.local/bin v0.6.0`. With Go, run `go install go.octolab.org/toolset/maintainer@v0.6.0`. For a manual installation, use a [v0.6.0 release archive](https://github.com/octomation/maintainer/releases/tag/v0.6.0). Run `maintainer version` to check the installed version. If you use the agent skill, [replace it](/agents/#keep-it-in-step) with the new binary’s copy.
